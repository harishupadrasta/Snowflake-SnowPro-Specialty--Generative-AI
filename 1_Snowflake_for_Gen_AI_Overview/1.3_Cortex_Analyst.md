# 1.3 Cortex Analyst

> **Exam Domain:** 1.0 — Snowflake for Gen AI Overview (18%)  
> **Exam Objective:** Understand Cortex Analyst, Semantic Views, VQR, and text-to-SQL capabilities

---

## What is Cortex Analyst?

Cortex Analyst is a **fully managed, LLM-powered text-to-SQL** engine that converts natural language questions into SQL queries over structured data. It uses **Semantic Views** to understand business context and generate accurate queries.

> 📘 **Key Terms**
>
> | Term | Definition |
> |------|-----------|
> | **Text-to-SQL** | Converting natural language questions into executable SQL |
> | **Semantic View** | Metadata layer defining metrics, dimensions, and relationships over tables |
> | **VQR** | Verified Query Representations — pre-validated SQL examples that improve accuracy |
> | **Agentic AI** | AI that autonomously plans and executes multi-step tasks |
>
> *See full [Glossary](../GLOSSARY.md)*

### Key Characteristics

| Feature | Description |
|---------|-------------|
| **Agentic AI** | Multi-model system selects best approach per query |
| **Semantic Views** | Metadata definitions that map business concepts to tables |
| **VQR** | Verified queries improve accuracy on common questions |
| **No training on your data** | LLMs never train on customer data |
| **RBAC-governed** | Respects existing Snowflake access controls |
| **Multi-turn** | Supports conversational follow-ups |

## Semantic Views

Semantic Views are **schema-level database objects** that define how business users think about data — bridging the gap between business terminology and physical table schemas.

### CREATE SEMANTIC VIEW

```sql
CREATE OR REPLACE SEMANTIC VIEW revenue_analytics

  TABLES (
    orders AS (
      SELECT * FROM analytics.fact_orders
      DESCRIPTION = 'Customer orders with revenue data'
    ),
    customers AS (
      SELECT * FROM analytics.dim_customers
      DESCRIPTION = 'Customer master data'
    )
  )

  RELATIONSHIPS (
    orders_to_customers AS (
      orders.customer_id REFERENCES customers.customer_id
    )
  )

  DIMENSIONS (
    customers.customer_name
      DESCRIPTION = 'Full legal name of the customer',
    customers.region
      DESCRIPTION = 'Geographic region: North America, EMEA, APAC',
    orders.order_date
      DESCRIPTION = 'Date the order was placed'
  )

  METRICS (
    orders.total_revenue AS SUM(orders.amount)
      DESCRIPTION = 'Total revenue from all orders',
    orders.avg_order_value AS AVG(orders.amount)
      DESCRIPTION = 'Average revenue per order'
  )

  AI_SQL_GENERATION 'Round all currency values to 2 decimal places.
    When no date filter is specified, default to the current fiscal year.'

  AI_QUESTION_CATEGORIZATION 'Reject questions about employee salaries.
    If the user asks about "revenue" without specifying a region, ask which region.'

  AI_VERIFIED_QUERIES (
    top_customers AS (
      QUESTION 'Who are our top 10 customers by revenue?'
      SQL 'SELECT customer_name, SUM(amount) as total_revenue 
           FROM __orders JOIN __customers 
           ON __orders.customer_id = __customers.customer_id
           GROUP BY customer_name ORDER BY total_revenue DESC LIMIT 10'
      VERIFIED_AT '2024-06-15'::TIMESTAMP
      VERIFIED_BY 'data_team'
      ONBOARDING_QUESTION TRUE
    )
  );
```

### Semantic View Components

| Component | Purpose | Example |
|-----------|---------|---------|
| **TABLES** | Logical tables (mapped to physical tables) | `orders AS (SELECT * FROM fact_orders)` |
| **RELATIONSHIPS** | How tables join | `orders.customer_id REFERENCES customers.id` |
| **DIMENSIONS** | Categorical/descriptive columns | Region, date, customer name |
| **FACTS** | Row-level quantitative values | Unit price, quantity |
| **METRICS** | Aggregated calculations | `SUM(amount)`, `COUNT(DISTINCT customer_id)` |

## Dimensions vs Facts vs Metrics

```
┌─────────────────────────────────────────────────────────┐
│                SEMANTIC VIEW HIERARCHY                    │
├─────────────────────────────────────────────────────────┤
│                                                           │
│  DIMENSIONS (categorical)         FACTS (row-level)       │
│  ├── customer_name                ├── unit_price          │
│  ├── region                       ├── quantity            │
│  ├── order_date                   └── discount_amount     │
│  └── product_category                                     │
│                                                           │
│  METRICS (aggregated)                                     │
│  ├── total_revenue = SUM(amount)                          │
│  ├── order_count = COUNT(*)                               │
│  └── avg_order_value = AVG(amount)                        │
│                                                           │
│  DERIVED METRICS (cross-table)                            │
│  └── revenue_per_customer = total_revenue / customer_count│
│                                                           │
└─────────────────────────────────────────────────────────┘
```

### Key Differences

| Concept | Scope | Aggregation | Example |
|---------|-------|-------------|---------|
| **Dimension** | Column-level | None (GROUP BY / WHERE) | `region`, `order_date` |
| **Fact** | Row-level | None (raw values) | `unit_price`, `quantity` |
| **Metric** | Aggregated | Always aggregated | `SUM(amount)`, `COUNT(*)` |
| **Derived Metric** | View-level | Combines metrics across tables | `revenue / customer_count` |

## Verified Query Representations (VQR)

VQRs are **question-SQL pairs** that Cortex Analyst uses as examples to improve accuracy on similar questions.

### How VQRs Work

1. User asks a question
2. Cortex Analyst checks if any VQR is semantically similar
3. If match found, uses the VQR as a template/guide for SQL generation
4. Response includes `confidence.verified_query_used` field

### VQR Rules (Exam-Critical)

- SQL must use **logical table names** prefixed with `__` (double underscore)
- Use column names from the semantic view, NOT physical table names
- Questions should be realistic user queries (not complete sentences required)
- Invalid/inaccurate VQRs **negatively impact** performance
- Mark good onboarding examples with `ONBOARDING_QUESTION TRUE`
- **Onboarding questions are ALWAYS displayed** to users as suggested starter questions, regardless of their current query or semantic similarity matching

### VQR + Custom Instructions Interaction

When both a relevant VQR and custom_instructions exist for a question:
- They are **complementary** (not overriding)
- **VQR** guides SQL structure and query patterns
- **Custom instructions** guide formatting, defaults, and behavioral rules
- Neither fully overrides the other — they work together
- Example: VQR provides the SQL template; instructions say "round to 2 decimal places"

### VQR in YAML Format (Legacy)

```yaml
verified_queries:
  - name: "monthly_revenue"
    question: "What was our revenue last month?"
    verified_at: 1714497970
    verified_by: "Jane Doe"
    use_as_onboarding_question: true
    sql: |
      SELECT SUM(amount) as revenue
      FROM __orders
      WHERE order_date >= DATEADD(month, -1, CURRENT_DATE())
        AND order_date < CURRENT_DATE()
```

## Custom Instructions

Two types of custom instructions control Cortex Analyst behavior:

### AI_SQL_GENERATION

Controls **how** SQL is generated:

```sql
AI_SQL_GENERATION '
  - Round all currency values to 2 decimal places
  - Use fiscal year (April-March) for year calculations
  - When filtering by quarter, Q1=Jan-Mar, Q2=Apr-Jun
  - Always include ORDER BY for top-N queries
'
```

### AI_QUESTION_CATEGORIZATION

Controls **how** questions are classified and handled:

```sql
AI_QUESTION_CATEGORIZATION '
  - Reject questions about employee compensation
  - If user asks about "sales" without a date range, ask for the time period
  - Questions about "churn" should use the customer_status = "churned" filter
'
```

> **Exam Tip:** When Cortex Analyst is used through Cortex Agents, write instructions in plain natural language (no state keywords like `UNCLEAR`).

## Calling Cortex Analyst

### REST API (Direct)

```
POST /api/v2/cortex/analyst/message

{
  "messages": [
    {"role": "user", "content": [{"type": "text", "text": "Top 10 customers by revenue?"}]}
  ],
  "semantic_view": "MY_DB.MY_SCHEMA.REVENUE_ANALYTICS"
}
```

### Response Types

| Content Type | Description |
|-------------|-------------|
| `text` | Natural language explanation |
| `sql` | Generated SQL query |
| `suggestions` | Follow-up question suggestions |

### Multi-Model Input Options

```json
{
  "semantic_view": "DB.SCHEMA.VIEW",           // Single semantic view
  "semantic_model_file": "@stage/model.yaml",  // Legacy YAML on stage
  "semantic_models": ["DB.SCHEMA.VIEW1", "DB.SCHEMA.VIEW2"]  // Multiple (auto-selects)
}
```

### Through Cortex Agents

```yaml
tools:
  - tool_spec:
      type: "cortex_analyst_text_to_sql"
      name: "RevenueAnalyst"
      description: "Answers revenue and sales questions"

tool_resources:
  RevenueAnalyst:
    semantic_view: "analytics.public.revenue_analytics"
```

## Access Control

### Required Roles

| Role | Access Level |
|------|-------------|
| `SNOWFLAKE.CORTEX_USER` | Full Cortex access (includes Analyst) |
| `SNOWFLAKE.CORTEX_ANALYST_USER` | **Analyst only** (least privilege) |

### Granting Access

```sql
-- Full Cortex access (includes Analyst)
GRANT DATABASE ROLE SNOWFLAKE.CORTEX_USER TO ROLE analyst_role;

-- Analyst-only access (most restrictive)
GRANT DATABASE ROLE SNOWFLAKE.CORTEX_ANALYST_USER TO ROLE analyst_role;

-- Also needed: SELECT on underlying tables
GRANT SELECT ON TABLE analytics.fact_orders TO ROLE analyst_role;
```

### Disabling Analyst Account-Wide

```sql
ALTER ACCOUNT SET ENABLE_CORTEX_ANALYST = FALSE;
```

## Evaluation and Testing

### Cortex Analyst Evaluations

Measures SQL generation accuracy against verified queries:

1. **Temporarily removes** selected VQRs from the semantic view
2. Asks those questions to Cortex Analyst (without the VQR guidance)
3. Compares generated SQL results against the VQR ground truth
4. Reports `sql_correctness` metric (LLM-as-judge)

### Running Evaluations

- **Snowsight:** AI & ML → Cortex Analyst → Select view → Evaluations tab
- **SQL:** `CALL EXECUTE_AI_EVALUATION('START', ...)`

### Improvement Workflow

```
Run Evaluation → Inspect Failures → Click "Improve" → Re-run Evaluation
```

## Best Practices (Exam-Critical)

1. **Start small** — 5-10 tables for initial proof of concept
2. **Write clear descriptions** for every table and column (most impactful for accuracy)
3. **Avoid synonyms** unless you have unique industry-specific terms
4. **Define relationships explicitly** — Cortex Analyst won't join without them
5. **Add metrics** for reusable aggregation calculations
6. **Use VQRs** only after tables/columns/descriptions are solid
7. **Separate instructions**: `sql_generation` for formatting, `question_categorization` for routing
8. **Keep model under ~100K tokens** to avoid LLM context pruning
9. **Use Cortex Search services** for high-cardinality text columns (>10 distinct values)
10. **Test with evaluations** before deploying to production

## Semantic SQL (Direct Querying)

Query semantic views directly without natural language:

```sql
SELECT * FROM SEMANTIC_VIEW(
  revenue_analytics
  METRICS orders.total_revenue, orders.order_count
  DIMENSIONS customers.region, orders.order_date
  WHERE orders.order_date >= '2024-01-01'
);
```

---

## Exam Tips

1. **Semantic Views replace YAML files** — they are native Snowflake objects with full RBAC
2. **VQR uses `__` prefix** for logical table names in SQL
3. **CORTEX_ANALYST_USER** is the least-privilege role for Analyst-only access
4. **Relationships must be defined** — no auto-join inference
5. **Derived metrics** can span multiple tables (view-level)
6. **NON ADDITIVE BY** handles semi-additive metrics (e.g., inventory snapshots)
7. **CUSTOM_INSTRUCTIONS** has two parts: sql_generation + question_categorization
8. **Evaluation uses LLM-as-judge** for sql_correctness scoring
